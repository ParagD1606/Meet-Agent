# Meeting extraction evaluation (PS-4)

How well does the meeting pipeline turn a transcript into the right tasks, owners, due dates and classifications, and does it stay safe when the transcript is ambiguous? This is the measured answer, with real models, on gold fixtures we wrote.

Run it yourself:

```bash
cd server
GOOGLE_APPLICATION_CREDENTIALS=/path/to/application_default_credentials.json \
  bun --env-file=../.env run scripts/meeting-eval.ts [--n 10] [--fixture ami-kickoff] [--mode final|live] [--json out.json] [--write]
bun test test/meeting-eval        # deterministic gate (no LLM): fixtures, scorer, adapter, loaders, baseline shape
```

It needs no database. The run stops before a meeting that would push the estimated cost past `--budget` (default $2; the estimate is an upper bound from the repo's price table). `--write` regenerates the results block below and `server/test/meeting-eval/baseline.json`.

## What is measured

| Metric | Definition |
|---|---|
| Task precision / recall / F1 | A predicted item matches a gold task when token-Jaccard of the titles is at least 0.5 (stop-words dropped, light stemming; an embedding similarity can be passed to `matchTasks`). Precision = predicted items matching some gold task / predicted. Recall = gold tasks matched by some prediction / gold. A merged duplicate still counts as recalled. Open questions and suggestions count as items too (they are in the gold with their label). |
| Owner accuracy | On one-to-one matched tasks: same person (first name or full name), or both null. A predicted owner on a gold-null task is wrong; a missing owner on a named task is wrong. Also reported only for tasks whose gold names an owner. |
| Due-date exact match | Same ISO date on matched tasks, null equals null; also reported for gold tasks that have a date. Relative phrases ("by Friday", "a week from tomorrow") must be resolved against the meeting date. |
| Classification accuracy + 4x4 confusion matrix | `confirmed` / `tentative` / `suggestion` / `question` on matched tasks. Pipeline items of kind `question` are labelled `question`. |
| Decision precision / recall | Token-Jaccard at least 0.4 on the decision sentence. |
| Duplicate detection rate | Planted duplicate pairs (the same task phrased twice) where the pipeline flagged one as a duplicate of the other, or merged them. False-duplicate rate = flagged items that are not part of a planted pair. |
| Conflict detection rate | Planted conflicts (same task, two due dates or two owners) where the pipeline flagged the pair. |
| Hallucination rate | Predicted items with no supporting quote in the transcript, using the same `quoteSupported` check the pipeline uses to drop invented items. |
| Approval safety | Of the items with an ambiguity flag (owner missing or ambiguous, duplicate, conflict), the share that were not auto-approved. |
| Latency | Wall time of the analysis call per meeting (includes the model call). |

`n/a` means the pipeline output does not carry that field, not a score of zero.

## Fixtures

`server/test/meeting-eval/gold/*.json`: 12 meetings, 57 to 73 turns each, written for this repo (the AMI and QMSum corpora are not downloaded or shipped).

- 4 AMI-style design-team meetings (remote control: project manager, industrial designer, UI designer, marketing) with disfluencies, cross-talk, decisions by show of hands.
- 3 QMSum-style excerpts (product meeting with role-named speakers, an academic research group, a parliamentary committee).
- 5 synthetic business meetings, including a stand-up, a brainstorm full of hypotheticals (2 real tasks in 62 turns), an all-hands full of past actions and chit-chat, a vendor review with planted duplicates and conflicts, and a hard case.
- Planted in the gold: relative dates, implicit owners ("I'll take that", "Sarah can do..."), suggestions ("maybe we should..."), unresolved questions ("who is going to talk to the supplier?"), duplicate pairs, due-date and owner conflicts, hypotheticals and completed past actions (negatives that make false positives measurable).
- Hard cases: pronoun owner ("she'll send it" refers to Sofia), dates relative to a stated date ("a week from tomorrow", "two weeks from Friday", "the day after the board meeting on the 30th").

Convention for the gold: `next <weekday>` and `this <weekday>` are only used where the transcript also says the day of the month, so the due date is unambiguous.

## Using the real corpora (optional, offline)

The loaders read a copy you downloaded yourself and never touch the network.

```bash
# AMI: download the "AMI manual annotations" package from https://groups.inf.ed.ac.uk/ami/corpus/ (licence applies), unzip it, then
bun run scripts/meeting-eval-loaders/ami.ts /path/to/ami_public_manual ./gold-ami --max 20
# QMSum: git clone https://github.com/Yale-LILY/QMSum, then
bun run scripts/meeting-eval-loaders/qmsum.ts /path/to/QMSum/data/ALL ./gold-qmsum --max 20
bun --env-file=../.env run scripts/meeting-eval.ts --dir ./gold-ami --mode live
```

AMI gives decision and action sentences (no owners, no dates) and QMSum gives decision/action queries with answers, so with these corpora only decision recall and task recall are meaningful, as a proxy; precision, owner, due and classification need the hand-labelled fixtures above. The AMI XML handling was written from the corpus documentation and tested on a hand-made sample only: check one real meeting first. Do not commit corpus data.

## Honest caveats

- Gold is small (12 meetings) and written by us, in the style of the corpora but not drawn from them; treat the numbers as a regression gate and a sanity check, not a benchmark claim.
- Scores come from one run at temperature 0; models still vary a little between runs, so differences of a few points are noise.
- Token-Jaccard at 0.5 is strict on titles: a correct task with a very different phrasing counts as a miss and a paraphrase counts as a hit only if enough words overlap.
- Metrics for duplicate/conflict detection, grounding and approval safety are only computed when the pipeline output carries those fields (see the notes in the results block). The adapter (`server/test/meeting-eval/adapter.ts`) is the only file to retarget when the pipeline's exports change.
